# Experience Manager Spec

## 1. Purpose & Scope

This manager is the **human bootstrap path** for Training-Free GRPO's experience pool. It is *not* a replacement for GRPO's automated extractor — it produces the **seed experiences** that GRPO will refine autonomously later. Two contributors (oscar, ankith) use this spec to collaboratively add, update, delete, and keep experiences derived from research sessions with Claude Code, Codex, or manual puzzle analysis.

## 2. Terminology

| Term | Meaning |
|---|---|
| **Experience** | One generalizable rule or heuristic for solving Alice's-Wonderland symbolic-transformation puzzles. One principle per entry. |
| **Manager session** | One invocation of this flow — one Claude conversation block that ends with confirmed writes. |
| **Operation** | `ADD`, `UPDATE`, `DELETE`, or `KEEP` — mirrors GRPO's `ADD/UPDATE/DELETE/NONE` logic. |
| **Source of truth** | `experiences.yaml` — the only file Claude writes during this flow. |

## 3. Files & Their Roles

| File | Role | Written by |
|---|---|---|
| `experiences.yaml` | Structured experience pool — source of truth. | Claude (after confirmation) |
| `archived_experiences.yaml` | Immutable archive of deleted entries. Append-only. | Claude (after confirmation) |
| `change_log.yaml` | Append-only session log for audit and rollback. | Claude (after confirmation) |
| `seed_experiences.yaml` | Flat GRPO-ready list (`"name: description"`). **Not touched here.** | User-owned flatten script |

> `seed_experiences.yaml` is regenerated by a separate script the user runs independently. Claude must never write or modify it.

## 4. Experience Schema

```yaml
- id: exp_001                                     # stable, monotonic; never reused after DELETE
  name: "RHS shorter implies compression"         # 3–5 words; becomes GRPO string prefix after flatten
  description: >                                  # 2–3 sentences; use "When [cond], [strategy]" if context-bound
    When the RHS has fewer symbols than the LHS, a reduction operation is at play.
    Look for repetitions, cancellations, or groupings that collapse multiple LHS
    symbols into fewer RHS symbols. Identifying that reduction pattern is usually
    the key step to recovering the hidden rule.
  example: |                                      # optional: concrete puzzle illustrating the rule
    LHS: !*[{   RHS: '"[   (4 → 3 symbols)
  constraints:                                    # optional: bullets bounding applicability
    - Applies to symbolic transformations only, not arithmetic-tier puzzles.
  tags: [pattern-matching, compression]           # optional: free-form labels for search/filter
  author: oscar                                   # required: oscar | ankith
  source_session: "Claude session 2026-05-22, Type-1 exploration"   # required
  discovered_from: "sample_id 12345"              # optional: puzzle id or rollout reference
  created_at: "2026-05-22T10:30:00Z"
  updated_at: "2026-05-22T10:30:00Z"
```

### ID allocation

- New `ADD` → next monotonic `exp_NNN` (zero-padded to 3 digits).
- IDs of deleted experiences are **never** reassigned. The archive holds them so cross-references remain valid.

## 5. Decision Rules

These rules are adapted from GRPO's own experience-update prompt
(`youtu-agent/utu/prompts/practice/experience.yaml`).

**Quality bar**
- Every experience must advance the learning objective: *help the agent infer symbolic transformation rules from examples and apply them precisely to new inputs.* Observations that don't move that needle → `KEEP` or `DELETE`.
- If the rule requires preconditions to hold universally, frame as **"When [condition], [strategy]"**.
- One principle per experience. If two ideas are entangled, split into two entries.
- `name` = 3–5 words. `description` = 2–3 sentences (condition + strategy + brief rationale).

**Choosing the operation**
| Operation | When to use |
|---|---|
| `ADD` | The insight is genuinely absent from every existing entry. |
| `UPDATE` | The insight refines, expands, or corrects an existing entry. Reuse the original `id`; bump `updated_at`. Synthesize — do not just concatenate. |
| `DELETE` | The entry contradicts new evidence, is demonstrably wrong, or is off-objective. Full record moves to `archived_experiences.yaml`. |
| `KEEP` | The content is already fully covered. No file changes. |

**Conflict resolution within one session**
- If multiple operations target the same `id`: `DELETE` > `UPDATE` > `ADD`.
- Multiple `ADD` proposals with overlapping content merge into one before confirmation.

## 6. Execution Flow

1. **Read** `experiences.yaml` (may be empty). Quote relevant existing entries by `id` when reasoning.
2. **Classify** the user's input — fact, rule, or observation — and propose one or more operations per the decision rules above.
3. **Draft** the full structured entries.
   - For `UPDATE`: show a diff (`before` → `after`).
   - For `DELETE`: show what will be archived and why.
4. **Confirm.** Present the complete proposed diff in one message. **Do not write anything until the user explicitly approves.** If the user partially agrees, iterate.
5. **Apply** (in this order after approval):
   1. Write/modify `experiences.yaml`.
   2. On `DELETE`, append the original record to `archived_experiences.yaml` (add `archived_at`, `archived_by`, `archived_reason` fields).
   3. Append a session entry to `change_log.yaml`.
6. **Report** the `session_id` and a one-line summary per operation.

## 7. Change Log Format

`change_log.yaml` is append-only. One entry per manager session:

```yaml
- session_id: "2026-05-22T10:30:00Z__oscar"
  author: oscar
  timestamp: "2026-05-22T10:30:00Z"
  summary: "Added compression rule; refined symbol-count heuristic."
  operations:
    - { op: ADD,    id: exp_007, after: "RHS shorter implies compression: When the RHS …" }
    - { op: UPDATE, id: exp_003, before: "Old text …", after: "New text …" }
    - { op: DELETE, id: exp_005, before: "Old text …", reason: "Contradicted by exp_007" }
```

**To inspect the last session:** read the final entry in `change_log.yaml`.

**To roll back a session:** reverse each operation in reverse order — re-instate deleted ids from `archived_experiences.yaml`, revert `UPDATE` bodies using the `before` field, remove `ADD`ed ids by id.
